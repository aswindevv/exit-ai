Critical mismatches

1. Manager Reject action does not exist in the UI at all. Backend Phase 5 testing confirmed rejection logic works server-side, but the Manager UI (ManagerPages.jsx) has exactly one mutation — useApprove() — used by Dashboard/KT-approvals/Clearances. No reject/escalate control exists anywhere. A live button-text dump across all 6 manager routes found zero "Reject" controls.

Aggravating: two real, currently-open seeded cases (Emp020, Emp009) already carry an "Escalated: manager rejected KT plan" task from prior backend activity, and it renders with the identical unlabeled "Review" button as a normal pending approval — a manager could click it and silently mark an HR escalation "done" with no way to actually record a reject.
Confirmed via source read + live Playwright button-text dump across all 6 routes.
2. IT UI cannot distinguish a verified execution from a failed one — false-success risk. rowStatus() in ItPages.jsx derives "Done" purely from exit_tasks.status, never from the actual agent_runs verification outcome. A disposable task with a real verification_failed agent_runs row rendered identically to a genuinely-verified one — "Done" — on Dashboard, Deprovisioning, and Audit Log.
Confirmed by constructing both outcomes on disposable rows and comparing rendered UI state.
3. Employee "Forward to HR" is broken. Clicking it after a RAG refusal produces zero HTTP response and a generic Supabase Edge Function dispatch error. Root cause (source-confirmed): a live Gmail SMTP send through the same sender account already exhausted (550 5.4.5 daily limit exceeded) by the resignation flow's email_drafting_agent, with no timeout/fallback. Employees currently cannot escalate an unanswered question to HR.

Functional mismatches

  • Exit-interview sentiment/summary agent writes real results to exit_interviews but creates no agent_runs row — unlike every other agent, a traceability gap (Employee).
  • risk/compliance/analytics agents are never logged by name in agent_runs — 196 rows have agent IS NULL, distinguished only by stage (HR).
  • manager_case_view has no status column (noted incidentally by the HR fork's schema inspection — flagged for the Manager area's attention, not independently re-verified in this pass).

Missing UI actions

  • Manager: Reject / escalate action (see Critical #1).
  • Manager: no visible escalation indicator or delegate notice, despite smart_routing (33 runs) and sla_escalation (1 run) executing server-side.
  • Employee: Notifications — no bell/list exists anywhere (source-confirmed).
  • HR: search/filter/sort on the all-exits list.

Broken UI actions

  • Employee: "Forward to HR" button (see Critical #3).
  • Cross-cutting, all 5 login screens: "Sign in with Microsoft" button has no onClick handler at all — a dead button with no corresponding backend/SSO integration documented anywhere in CLAUDE.md's secrets list.

Security mismatches

No security mismatches found. HR-only field protection verified at the database level, independently by two forks (Employee, Manager, IT confirmed the negative case from their own sessions; HR confirmed the positive case and the schema-level enforcement):
  • pg_policies on exit_cases: exactly 2 policies, both role=hr (exit_cases_hr_select, exit_cases_hr_relieving_letter). No policy exists for employee/manager/it/finance on the base table.
  • pg_policies on exit_interviews: employee gets INSERT-only (no read-back); HR gets SELECT.
  • information_schema.columns on employee_exit_view, manager_case_view, it_task_view, finance_case_view, employee_interview_status_view: none expose risk_level, risk_score, rehire_eligible, sentiment, summary, themes, or rehire_reason.
  • Employee/manager/IT authenticated-client probes against HR-only fields all returned empty results, confirming real RLS filtering rather than coincidentally-empty tables.
The 5 intentional security_invoker=false role views were not touched. RLS was not weakened by any fork to make a test pass.

Visual / browser issues

  • No broken layouts, missing components, or blank pages found on any of the 4 roles' pages tested.
  • Zero unresolved console errors across Employee, Manager, HR; IT reached zero only after the audit fixed a stale local agents.service process left over from before service.py's last edit (an audit-environment artifact, not a shipped defect).

Database verification

  • Baseline confirmed at audit start: exactly 20 real exit_cases (Emp001–Emp020), statuses unchanged throughout.
  • Independent final re-verification (run directly, not just fork self-report): exit_cases count = 20, employee_id list and statuses identical to the pre-audit baseline.
  • Zero leftover rows for any disposable test identity used (Emp050, Emp060, Emp061, Emp070, Emp080) across exit_cases, and no orphaned non-employee-role profiles under those IDs.
  • IT fork's self-disclosed incident (an unscoped locator briefly clicked a real Emp010 task and logged one agent_runs row before being caught) — independently re-checked: Emp010's task set matches an internally-consistent pre-existing state with no agent_runs rows newer than 2026-09-13 (i.e. no stray incident row survived), consistent with the fork's own claim of detection + full revert + reverification.
  • HR-only field RLS/view enforcement verified directly via pg_policies and information_schema.columns (see Security section) — read-only inspection, nothing modified.
  • No real production email was sent; the one real Gmail send attempted (resignation → email_drafting_agent) hit a genuine daily quota limit and was logged, not fabricated.

Console / network errors

  • Environmental, not app defects: 500 POST /activate-exit and the Forward-to-HR dispatch failure both trace to the same exhausted demo Gmail sending account (real daily limit hit) — not a code defect, but see Critical #3 for the UI-facing consequence (no timeout/fallback).
  • Test-environment artifact: IT's initial 404 on the deprovisioning endpoint, caused by a stale local agents.service process pre-dating a recent code edit — resolved by restarting the service; not a shipped defect.
  • Benign: one ERR_ABORTED network entry on HR logout — cosmetic, no functional impact.
  • No other console errors or 4xx/5xx responses were observed across any of the 4 roles' full navigation + action sessions.

Recommended fixes — prioritized list only, not implemented

  1. Add a Reject/Escalate action to the Manager UI, and visually distinguish an already-escalated task from a normal pending approval (Critical #1).
  2. Make the IT UI surface the actual agent_runs verification outcome (verified vs. verification_failed) instead of deriving status only from exit_tasks.status (Critical #2).
  3. Fix or guard "Forward to HR": add a timeout/fallback so a Gmail send failure surfaces a clear, actionable error instead of a bare dispatch failure (Critical #3).
  4. Remove or wire the dead "Sign in with Microsoft" button on the shared login page.
  5. Surface backend-only agent activity (smart_routing, sla_escalation, multi_system_clearance) somewhere in the Manager UI so escalations/delegate routing aren't invisible.
  6. Add an agent_runs row for the exit-interview sentiment/summary agent, and populate agent (not just stage) for risk/compliance/analytics runs, for consistent traceability.
  7. Add search/filter/sort to the HR all-exits list.
  8. Add a Notifications feature to the Employee dashboard (or confirm it was intentionally deferred).

Audit performed via 4 parallel Playwright sessions (Employee/Manager/IT/HR), each cross-checked against the live Supabase project via direct SQL. No fixes, redesign, backend, database, RLS, or agent changes were made. No git actions taken.
