1. Project overview

What ExitAI is

ExitAI is a web application that runs the whole process of an employee leaving a company — "offboarding" or "exit clearance" — with a team of AI agents doing the coordination work that a person would otherwise chase by email.

An employee submits their resignation in the app. From that moment the system generates their personal exit checklist, tells their manager, tracks knowledge handover, generates the IT deprovisioning plan, verifies compliance (NDA, assets, access), waits for Finance to settle dues, assesses risk and rehire eligibility from the exit interview, and finally issues the relieving letter. Five people see five different dashboards, each showing only what their role is responsible for.

The problem it solves

Problem with manual offboardingWhat ExitAI does about it
Exit checklists are copy-pasted and generic, so role-specific handover gets missed. An LLM generates the checklist from the employee's actual role and department, with due dates derived from their last working day.
Nobody knows who is currently blocking a clearance. Chasing happens over email and gets dropped. Every task has a stage, an owner and a due date in one database. The SLA agent names the specific blocker, how many days late, and the downstream impact.
An employee "leaves" but their accounts stay live for weeks because IT was told too late. The IT deprovisioning plan is generated automatically the moment the manager signs off knowledge transfer — not after someone remembers to raise a ticket.
Final clearance gets signed while the NDA is unreturned or a laptop is missing, and no one notices until audit. A compliance agent blocks final clearance and names the exact missing item. It cannot be bypassed in the UI, because the relieving-letter gate is enforced by a database function.
Exit interviews are filed and never read, so the same attrition cause repeats. Each interview is summarised with sentiment and themes; a longitudinal agent counts themes across all interviews and raises a rising-theme alert per department.
Exiting employees keep asking HR the same questions about notice period, settlement, and documents. A RAG chatbot answers from the company's actual exit policy document, with citations, and refuses to invent company-specific facts.
Sensitive assessments (risk score, rehire eligibility, interview sentiment) leak to managers. Those columns are HR-only and enforced in the database with row-level security plus restricted views — not merely hidden in the UI.

3. What RAG is, in this project

The plain-language version

A language model does not know your company's exit policy. You could paste the whole policy into every question, but that is expensive and the model loses the thread in long text. RAG — Retrieval-Augmented Generation — is the cheap fix: keep the policy in a database, fetch only the two or three passages that actually relate to the question, and hand just those to the model along with the question. The model answers from what it was handed, and you can show the employee which sections the answer came from.

The five steps, and exactly what each one is here

StepWhat happensThe concrete implementation in this repo
1. Chunk Split the document into passages small enough to be precise. scripts/ingest_docs.js reads scripts/exit_policy.md and splits on section headings — a new chunk starts at every §n.n Title line, and following paragraphs attach to it. One chunk = one policy section, deliberately, so a citation can never point at section 4.1 for text that actually came from 4.2. Result: 67 chunks currently in the table.
2. Embed Turn each chunk into a list of numbers (a vector) that encodes its meaning. POST {PORTKEY_BASE_URL}/v1/embeddings with OpenAI text-embedding-3-small (1536 dimensions) via the Portkey virtual key. The script asserts embedding.length === 1536 before inserting, so a model change fails on ingest rather than at query time.
3. Store Save chunk text + vector so you can search by meaning. Table exit_docs — id, source, section, content, embedding vector(1536) — with an HNSW index using vector_cosine_ops. HNSW was chosen over ivfflat because ivfflat needs training data and returns poor results until the table is large; HNSW works correctly from the very first row. Ingest is idempotent: it deletes prior rows for that source before re-inserting.
4. Retrieve Embed the question the same way, find the nearest chunks. SQL function match_exit_docs(query_embedding vector(1536), match_count int default 4) (migration 0003_rag.sql). It orders by pgvector's cosine-distance operator <=> and returns 1 - distance as a similarity score. The app requests top-k = 4.
5. Generate Give the model the retrieved text plus the question; it answers from that. Edge Function supabase/functions/ask. Builds the prompt as [Section title]\ncontent blocks, calls gpt-5.6-sol through Portkey, and returns { answer, sources, refused, general } to the browser.

What makes this implementation careful rather than naive

  • The model reports its own citations as data, not prose. It must return a JSON object with a sections array listing the section titles it used. The UI renders the citation line from that array. A naive version lets the model write "Sources: …" into its answer, which then disagrees with whatever the UI lists separately.
  • Three-way scope, not two. scope is policy (the context answers it), general (not in the policy, but it is a reasonable work question — give general guidance and never state a company-specific number as if it were this company's rule), or refused (nothing to do with work — one sentence, contact HR). This distinction matters because an employee will act on a notice period or a settlement figure; an invented one is the failure that actually hurts.
  • A similarity floor. Below cosine similarity 0.35 the top chunk is not genuinely relevant (greetings, chit-chat), so the answer is still returned but no citations are attached — unrelated sections are never shown as if they grounded it.
  • A refusal fallback path. If the model ignores the JSON contract, a wording heuristic classifies "I don't have…" as a refusal, so the employee still gets the Forward to HR button rather than a dead end.
  • Forward-to-HR never silently fails. If Gmail SMTP times out (8 s cap), the forward-to-hr function writes the question to agent_runs with status='delivery_failed' and tells the employee the truth — that it is logged and may be delayed — instead of showing a generic error.

Why pgvector instead of a dedicated vector database

ReasonDetail
One database, one backup, one set of credentials Pinecone/Weaviate/Qdrant would be a second managed service with its own key, SDK, billing, uptime and backup story. The corpus here is 67 chunks of one policy document — that does not justify a second system.
Security actually composes This is the decisive reason. exit_docs has RLS enabled with zero policies, so the browser's anon key reads nothing from it. And match_exit_docs is deliberately not SECURITY DEFINER, so it runs with the caller's rights and inherits that same denial. The only path to the corpus is the service-key /ask function — which makes /ask a genuine security boundary where questions can be logged, rate-limited and redacted, not a convenience wrapper around a table the browser could already read. An external vector DB would sit outside Postgres' permission model entirely, and you would have to rebuild that boundary by hand.
No sync problem A separate vector store must be kept consistent with the relational data. Here a chunk is a row in the same database as everything else; there is nothing to drift.
Joins are free A retrieved chunk can be joined to any other table in the same query. Across a network boundary that becomes application-side stitching.
HNSW is good enough at this scale Dedicated vector DBs earn their keep at millions of vectors with sharding and filtered search. At 67 — or 67,000 — a Postgres HNSW index answers in single-digit milliseconds.

4. Architecture — hub and spoke

The pattern

Hub-and-spoke means one Supervisor agent (the hub) owns the case and decides which specialist agent (a spoke) runs next. Spokes never talk to each other. The IT agent does not call the Finance agent; it returns to the hub, and the hub decides.

This is a deliberate choice over letting agents call each other freely. With one hub there is exactly one place that knows the order of stages, one place that handles a rejection, and one ordered trace to read when something goes wrong. Free-form agent-to-agent messaging gives you emergent loops and no single point to reason about.

Naming note, in case it comes up. "Hub-and-spoke" here is an architecture pattern. It has nothing to do with HubSpot — there is no CRM anywhere in this project. Likewise the agent framework is LangGraph, not CrewAI.

#15 Multi-System Clearance — what "demo stand-in" precisely means. There is one Supabase project here, not three integrated enterprise platforms. So HRMSAdapter queries our exit_tasks where stage = 'hr' (plus the NDA document), ITAMAdapter queries stage = 'it' (plus asset documents), and FinanceAdapter queries stage = 'finance'. Every query is a real live query — no hardcoded status values. What is stand-in is which system is being asked. The adapter contract above them is production-shaped, so swapping in a real HRMS means overriding one _fetch() method per adapter and changing nothing else in the file. A live run produced: it=cleared, hrms=pending ["Complete exit interview"], finance=pending ["Clear final settlement dues"], overall=pending.

#18 IT Deprovisioning — what is mock and what is not. Real: the LLM-generated plan, the human approval click, the RLS-scoped status write, the independent verification logic, and the per-task audit row. Mock: the adapter that would call Okta / Jamf / Google Workspace. The module's own docstring states the reason plainly — "a task marked done is not proof deprovisioning actually executed" — so the execute/verify/audit layer was built even though the provider behind it is a stand-in. Two fault-injection adapters (_AlwaysFailAdapter, _AlwaysTimeoutAdapter) exist specifically to prove the verification step can fail.

#11 Smart Routing — the branch that never fires. Department-match is real code over a real column, but in the current dataset no HR / manager / IT profile has a non-null department (only employees do), so that branch always falls through to the full candidate pool. The out-of-office branch is exercised and verified. Ordering of "primary" vs "delegate" comes from profiles.created_at, i.e. real insert order, not a hardcoded name.

#12 Risk — tenure is a proxy, and it matters. There is no hire_date column anywhere in the schema. Tenure risk is derived from profiles.created_at instead. Because all seed profiles were created recently, every case currently reads as short tenure (0.9). The weighting and thresholds are real; that one input is not yet. If asked "is the risk score real?" — the arithmetic is, one of its four inputs is a placeholder until onboarding data exists.

#6 Email — "drafting" is templating, not generation. The brief describes LLM-drafted emails. In practice notifications.py composes from structured templates with no LLM call, for the same reason the finance agent has none: these are fixed transactional notices where a model adds cost and variance and no value. The email_drafting_agent layer adds routing, tracing, and honest outcome recording on top.

8.2 The security model, and why it is built this way

The frontend holds the anon key, which any user can read out of the JavaScript bundle. So the frontend cannot be where permissions are decided. Postgres is.

Layer 1 — default deny

RLS is enabled on every table. A table with RLS on and no matching policy returns zero rows and rejects writes. Nothing is visible unless a policy says so.

Layer 2 — one role helper

app_current_role() returns the caller's role. It is SECURITY DEFINER so it can read profiles while profiles is itself under RLS, and it sets search_path = '' with fully-qualified names — so an attacker cannot shadow profiles with an object in a schema they control and have the definer function resolve to it. Execute is granted to authenticated only.

Layer 3 — the HR-only columns

exit_cases has one SELECT policy, for HR. There is no employee policy and no manager policy — deliberately. Adding one would hand that role the whole row, including risk_score, risk_level and rehire_eligible.

Layer 4 — restricted views as the only other way in

Five views run with security_invoker = false, i.e. as the view owner, so they can see past that HR-only policy — and their fixed SELECT list decides what the caller actually gets. Each view self-filters on auth.uid().

ViewForExposes
employee_exit_viewEmployeeid, employee_name, department, role_title, last_working_day (+ relieving fields)
manager_case_viewManagerSame safe columns, filtered to manager_id = auth.uid()
it_task_viewITstage='it' tasks + employee name/department + the latest verification status via a lateral join
finance_case_viewFinanceSafe columns + finance_cleared + dues_note
employee_interview_status_viewEmployeecase_id + created_at only — enough for "have I submitted?", nothing more

None of these views may ever gain a risk or rehire column. That is stated in a comment on each view in the migration.

The Supabase Advisor warning you will be asked about. Supabase's Advisor reports "Security Definer View" as an ERROR on all five views and suggests setting security_invoker = on. That suggestion is wrong for this schema and has broken the dashboards three times. With invoker semantics the view runs as the caller, who has no policy on exit_cases — so it returns zero rows and the dashboard goes blank. The views are safe precisely because their column list is fixed and they self-filter on auth.uid(). The fix for a zero-row dashboard is to re-run 0020_role_views_security_invoker.sql.

Layer 5 — write paths are narrower than read paths

  • Finance writes through an RPC, not an UPDATE policy. exit_cases has no SELECT policy for finance by design. Postgres cannot apply an UPDATE's WHERE clause to a row the caller cannot see — so a plain RLS UPDATE policy silently matches zero rows. Hence finance_mark_dues_settled: SECURITY DEFINER, checks the caller's role itself, and forward-only (always sets finance_cleared = true). This is a genuinely non-obvious interaction and a good thing to be able to explain.
  • Column-level grants. GRANT UPDATE (finance_cleared, dues_note) — an authenticated caller can write those two columns and nothing else.
  • Forward-only approvals. The finance UPDATE policy's WITH CHECK pins finance_cleared = true, so the surface cannot be used to un-clear a case.
  • The relieving gate is re-checked in the database. The HR update policy's WITH CHECK calls exit_case_cleared_for_relieving(id), which requires finance_cleared, zero non-done tasks across all four stages, and all four stages present. Bypassing the UI does not bypass this.
  • Storage is scoped by path. The bucket policy checks storage.foldername(name)[1] is a case the caller owns, so an employee cannot upload into, or read, another person's folder.
  • Identity is never taken from the request body. Both writing Edge Functions derive the employee from the caller's own JWT.

13. Q&A — 27 questions a manager or director might ask

Plain-language answers to the questions most likely to come up in a review or demo. Questions already answered in §10's callout are repeated here for completeness.

The AI and what it does

1. Is it really multi-agent, or just one script with a few functions?

It is a LangGraph StateGraph with seven stage nodes and a real conditional edge (approve → IT path, reject → escalation path). Each spoke is its own compiled subgraph in its own Python module, individually runnable from the CLI. agent_runs holds 323 real stage transitions from past runs, one row per agent invocation.

2. How many agents actually call the AI model?

Nine of the 24 numbered roles. The other fourteen are deterministic Python — arithmetic, regex keyword matching, date comparison, or database queries. See §11 for the full breakdown.

3. How is the LLM prompted? Does it see sensitive employee data?

For the checklist, the model receives only the employee's role title and department — not their name, resignation reason, or salary. For the interview summarizer, it receives the full free-text interview transcript. For the RAG assistant, it receives retrieved policy text plus the employee's typed question. The model never sees passwords, keys, or any data from other employees' cases.

4. What happens if the AI generates a wrong or poor checklist?

Two guards exist. First, the Python agent drops any task the model misfiles into the wrong category (e.g. "Revoke GitHub access" appearing in the manager list) using a regex filter. Second, the checklist is reviewed by the employee and HR — a generated task that does not make sense for the role will be caught before it matters. The checklist is a starting point, not an approved instruction.

5. Why do some agents not use AI at all?

When the answer is a fixed rule or a number — "are all prior stages done?", "does this file contain the word NDA?", "how many days overdue?" — a model adds latency, cost, and hallucination risk without adding value. Every place where an LLM was deliberately not used is called out in §11.2 with the specific reason.

6. What if the AI gives a hallucinated answer in the RAG chatbot?

Two containment layers. First, the prompt instructs the model to answer only from the retrieved context for company-specific facts, and to refuse to state a notice period or settlement amount it cannot find in context. Second, if the model still produces a "don't have" phrasing, the code classifies it as a refusal and shows the employee a "Forward to HR" button instead of displaying the answer as company policy. The most dangerous failure — a confidently stated wrong notice period — is the case the prompt is designed to prevent.

7. Can the AI refuse to process an exit case?

No. The only agent that calls the model for case processing is the checklist generator and the IT planner — both are triggered automatically and both produce JSON. If the model returns malformed JSON or errors, the Python code raises an exception and the case stays in its current state. The human gates (manager, finance, HR) still function regardless.

Privacy and data

8. What data does ExitAI store about an employee?

Profile (name, email, department, role), exit case (last working day, resignation reason, manager/HR assigned, clearance status), tasks (checklist items and their status), uploaded documents (stored in a private Supabase Storage bucket), and the exit interview (free-text responses). For HR only: the LLM-generated interview summary, sentiment, themes, rehire eligibility, and risk score. Nothing about current (non-exiting) employees beyond what exists in profiles for login purposes.

9. Can an employee see their own risk score or interview feedback?

No. risk_score, risk_level, rehire_eligible, and the interview summary / sentiment / themes are stored in columns that have exactly one SELECT policy in the database: HR only. The employee's view of their case exposes five safe columns (name, department, role, last working day, relieving letter status) and no assessment fields. This was tested directly: logging in as an employee and querying the table returns zero assessment-column data.

10. How is the employee's privacy protected between roles?

Row Level Security in Postgres enforces it, not the UI. A manager can only see cases where they are the assigned manager_id. IT sees only stage='it' tasks for active cases. Finance sees safe columns plus the clearance flag — it cannot read assessment fields even with a direct database query. The frontend holds only the anon key (public, RLS-constrained); no role can see another role's data because there is no policy granting it.

11. What happens to an employee's data after they are cleared?

The rows remain in the database — the case status moves to "completed", relieving_letter_issued becomes true, and the rows are auditable. There is no automated deletion or anonymisation built yet. In a production deployment you would add a data-retention policy (e.g. archive after N years), but that is out of scope for this build.

The mock and manual parts

12. Which parts are actually automated end to end?

Everything between the human gates fires without anyone clicking anything: checklist generation, KT calendar booking, OCR document validation, interview summarisation, IT plan generation, compliance re-checking after every action, finance clearance evaluation, risk scoring, and the relieving-letter email. The three deliberate human gates are the manager's KT sign-off, the finance dues settlement, and HR's issue-relieving-letter click. The IT agent also never marks its own tasks done — IT staff approve each item individually.

13. What would it take to make the mock IT execution part real?

In agents/spokes/it_deprovisioning_agent.py, replace MockITAdapter with an adapter that calls the real provider (Okta's /api/v1/users/{id}/lifecycle/deactivate, Jamf's device management API, or Google Workspace's Admin SDK). The verification logic, the audit row, and the error handling already exist and work — only the one _execute() method changes. Estimated: a day per provider, plus integration testing.

14. What would it take to make the multi-system clearance real?

Override _fetch() on each of the three adapter classes (HRMSAdapter, ITAMAdapter, FinanceAdapter) to call the real external API instead of querying the local Supabase table. The contract — timeouts, retries, status codes, error capture — is already built. You would need API credentials for each system and a mapping from Supabase employee IDs to the external system's user IDs.

15. The six "periodic" agents — how do they actually run?

By hand, from the command line, whenever someone remembers to run them. There is no scheduler, cron job, or GitHub Action anywhere in the repo. Adding recurrence is a small job — a pg_cron entry or a system-level scheduled task calling the existing python -m agents.<name> entry points — but it is not built. This is stated plainly in §10.2.

Building and architecture

16. What does "hub and spoke" mean in practice?

The Supervisor (#20) is the hub — one LangGraph graph that owns the case state and calls each domain agent in sequence. Each domain agent (HR, IT, Finance, Compliance, Risk) is a spoke — its own compiled subgraph that can run standalone from the CLI and knows nothing about the other spokes. Spokes never call each other; everything goes through the hub. This means adding a new agent is adding a new spoke and wiring it into one place in supervisor.py.

17. How would you add a new agent to this system?

Four steps: (1) Write a new subgraph in agents/spokes/ or agents/analytics/ using the same StateGraph pattern. (2) If it uses the LLM, add a prompt file under prompts/ and load it with load_prompt(). (3) Wire it into supervisor.py by importing the subgraph and adding one node and one edge. (4) Add an entry point to service.py if the frontend needs to trigger it. The tracing, DB logging, and email routing are all in shared core modules — the new agent just calls them.

18. How is this different from just a spreadsheet or a shared task list?

Three things a spreadsheet cannot do: (1) generate a role-specific checklist automatically when an employee resigns, (2) enforce the clearance sequence in the database so a relieving letter cannot be issued even if someone tries to skip steps, and (3) surface escalations automatically when tasks go overdue — naming the specific blocker and downstream impact. A spreadsheet also cannot gate the IT deprovisioning plan on manager approval, or verify that an uploaded document actually contains an NDA signature.

19. What is the cost per exit, roughly?

The LLM is called nine times per case during a normal end-to-end run: checklist (1), IT plan (1), interview summary (1), and analytics/audit narratives (up to 4, run manually). At current Azure OpenAI pricing through Portkey, each call processes a few hundred tokens in and a few hundred out. The total per-case LLM cost is well under $0.10 at demo scale. The dominant cost in production would be Supabase's compute and storage tier, not the model calls.

20. How would this scale to 1,000 exits per month?

The bottleneck would be the Python agent service — currently a single-threaded stdlib HTTP server on one developer's laptop. For production you would containerise it (it has no shared state between requests) and put it behind a load balancer, or replace it with Supabase Edge Functions. The database (Supabase Postgres) and the LLM calls (through Portkey) are already horizontally scalable. The six manual analytics agents would need the scheduler that is currently missing.

The build itself

21. What did you build vs. what did the AI tool do?

I designed the architecture, wrote every agent, wrote every migration, built all five dashboards, and debugged everything. The AI tool (Claude) was used as a coding assistant — it suggested code given my instructions, which I reviewed, modified, and tested. Every design decision — which agents use the LLM, how the security model works, which parts are deterministic, the hub-and-spoke topology — was made by me. The AI did not design the system; I used it the way you would use a fast autocomplete that can write a LangGraph node when you describe what it should do.

22. How long did this take to build?

Roughly [the builder should fill in their own timeline here — this field intentionally left blank to avoid a number that becomes inaccurate over time]. The project spans 24 agents, 5 role dashboards, 28 database migrations, 3 Edge Functions, and end-to-end Playwright verification scripts. The hardest part was not writing the code — it was understanding the cascade effects of Supabase's security_invoker setting and getting the RLS model right so each role can only see exactly what they should.

23. What was the hardest bug to fix?

The security-invoker view drift. Five Postgres views must run as their owner (not the caller) so they can see past HR-only RLS and expose a safe column subset. Supabase's own Advisor repeatedly recommended flipping them to security_invoker = on — the correct setting for most views, but wrong here — and applying that recommendation wiped every non-HR dashboard. The fix is migration 0020, which re-asserts security_invoker = false; the CLAUDE.md non-negotiables section explicitly says never apply the Advisor's suggestion for these five views, because this bug has occurred three times.

24. What happens if the model provider (Azure OpenAI via Portkey) is unavailable?

The checklist and IT plan generation fail with an HTTP error. The Python service returns a 500 to the frontend. The case row and any already-written task rows remain intact — nothing is corrupted. The human gates (manager, finance, HR) still function because they write directly to Supabase through the frontend, bypassing the agent service entirely. A resume is as simple as re-triggering the failed action once the model is back.

25. Is there any risk the AI misclassifies someone's exit as "high risk" incorrectly?

Yes, and it is disclosed. The risk score is a weighted formula over four inputs — three of which are real (department criticality, interview sentiment, task completion fraction) and one of which is a known proxy (tenure is derived from profiles.created_at because no hire_date column exists). Because all seed profiles were created recently, every case currently reads as short tenure and gets the maximum tenure-risk weight. The score is visible to HR only, as one signal among several — not an automated decision. A reviewable number that is slightly wrong is better than a hidden one.

26. Can you demonstrate it live?

Yes — the system is running against a live Supabase project with 107 demo profiles and 27 exit cases. The agent service needs to be started locally (PYTHONIOENCODING=utf-8 python -m agents.service) alongside the Vite dev server (npm run dev). Five demo accounts exist (see §9), each with a different role. A resignation-to-relieving-letter run takes about 10 minutes of clicking through the five dashboards with the terminal trace visible in a side pane.

27. What would a production version need that this demo does not have?

A scheduler for the six manual analytics agents. Real IT execution adapters (Okta/Jamf/Google Workspace) replacing the mock. Real external system adapters for the multi-system clearance. A hire_date column for accurate tenure scoring. A data-retention/deletion policy. The KT document upload UI (currently CLI-only). And the single complete five-role browser review (Phase 9, still open). Everything else — the agents, the security model, the database, the email/calendar integrations, the RAG assistant — is built and runs against real data.
